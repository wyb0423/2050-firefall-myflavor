# 诊断与验证

## 证据层级

“功能不生效”至少可能发生在五层：

1. 文件未被加载或被后加载内容覆盖；
2. 顶层定义解析失败；
3. 调度入口未运行；
4. trigger 未成立或作用域错误；
5. effect 执行后被其他系统覆盖或回滚。

为每层寻找独立证据，避免只看到定义存在就断言功能已运行。

## 日志读取

检查用户文档目录中的 `debug.log`、`error.log`、`game.log` 及轮转文件。先按修改时间列出文件，再跨全部轮转日志搜索；大日志可能在几分钟内轮转。

为复杂流程使用稳定前缀、对象 ID、状态和关联 ID。典型生命周期可记录：

```text
SCHEDULER_REACHED
CANDIDATE_CREATED
EFFECT_APPLIED
EVALUATION_PASSED / EVALUATION_FAILED
KEPT / ROLLED_BACK / CANCELLED
```

候选出现不等于效果执行，效果执行不等于最终保留。日志最好包含国家、州或目标对象，避免多个实例在同一时间产生无法区分的重复记录。

生成文件的行号会变化。关联时优先使用稳定技术 ID 和上下文，不要把旧行号当作长期标识。

## 错误归因

判断错误是否属于目标 Mod时，核对：

- `Script location` 的相对路径；
- 当前加载栈中最终提供该路径或顶层键的 Mod；
- 错误时间与功能触发时间；
- 目标 Mod 是否注入、替换或调用了相关定义。

同一运行中出现的无关错误不能自动归因于当前 Mod；反过来，没有 error 也不能证明某个运行时分支到达。

## 静态与生成器验证

适用时检查：

- 目标目录和元数据完整；
- 顶层键无意外重复；
- 花括号、字符串和注释结构正常；
- 本地化键存在；
- 引用的 trigger、effect、modifier、PM、PMG、building 和 event 均存在于最终加载栈；
- 生成器两次输出哈希一致；
- 生成数量、覆盖集合、排除集合和稳定 ID 符合断言；
- 文件编码符合游戏和项目约定。

括号平衡只是最低检查，不证明语法、作用域或逻辑正确。

## 运行时验收

为修改建立最小可控场景：

1. 验证入口可见或调度器到达；
2. 让正向条件成立并观察效果；
3. 让失败或取消条件成立，验证清理和回滚；
4. 检查其他 Mod 是否随后覆盖结果；
5. 重载存档，验证持久状态和迁移；
6. 检查 AI 与玩家路径是否按设计不同。

交付时区分：已静态确认、已由生成器断言、已由日志确认、尚需游戏内目测。
