# 建筑与生产方式

## 最终数据图

针对当前加载栈建立：

```text
building -> production method groups -> production methods
production method -> unlocks + workforce/level/state modifiers + goods deltas
```

同时记录 building group、所有权、是否可补贴、是否属于政府/军事/生计/基础设施，以及其他会改变经济解释的属性。

## PMG 的语义

PMG 列表顺序可能表示技术升级，但也可能表示：

- 互斥产品方向；
- 副产品或专精；
- 所有权；
- 训练、征兵或军事配置；
- 同级替代方案。

不要假定所有 PMG 都是线性升级链。自动处理前按 PMG 语义分类；不明确时保持人工控制或只允许明确方向。

## 比较商品变化

对每个商品计算来源 PM 到目标 PM 的净变化，不要仅按字段前缀判断：

- 正的 input 通常增加消费；
- 负的 input 可能减少消费；
- 正的 output 通常增加产出；
- 负的 output 可能表示消费或牺牲其他产出。

把字面量数值、脚本化数值和缺失字段区分开。解析器不能确定经济含义时，应把该转移列为需要人工审查，而不是生成看似精确的价格条件。

## 自动管理设计

如果任务需要自动选择 PM，先决定目标函数：利润、就业、吞吐、产出、投入安全、人均指标或用户指定组合。不同建筑类别可能需要不同目标。

稳健的试运行系统通常包含：

```text
候选条件持续成立
  -> 捕获切换前基线
  -> 只改变一个可归因对象
  -> 观察足够周期
  -> 连续验收
       -> 保留并冷却
       -> 回滚并冷却
```

根据风险增加紧急回滚、外部修改检测、手动保护、方向反转检测和震荡锁。入口条件只表示“值得尝试”，不能替代切换后的结果验证。

## 多管理器兼容

当多个 Mod 都会修改 PM：

- 列出每个调度入口和实际写入 effect；
- 确认设置变量由谁提供和读取；
- 对完整覆盖的建筑或 PMG 进行精准委托；
- 未覆盖对象继续交给原系统；
- 避免一个系统降级后另一个系统立即升级；
- 在 UI 中说明哪些设置入口仍需启用。

分类应基于上游实际引用的 PM 和最终建筑挂载关系，名称启发式只能作为辅助。

## 覆盖验证

至少比较建筑、PMG、PM 和上游实际“建筑—PM”组合。生成的降级边应有反向升级边；有意排除、非线性 PMG 和无有效建筑挂载的孤立对象应出现在报告中。
