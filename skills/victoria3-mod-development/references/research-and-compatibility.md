# 调研与兼容性

## 权威来源与边界

先确认游戏版本、游戏根目录、用户 Mod 目录、Workshop 根目录、依赖 Mod ID、目标 Mod 和预期加载顺序。路径属于环境输入，应参数化或仅写入本地配置，不应成为可移植实现的一部分。

证据优先级通常为：

1. 当前安装版本的原版文件；
2. 当前安装的依赖 Mod 文件；
3. 启动后的解析和运行日志；
4. 对应版本的官方文档、Wiki 或开发者说明；
5. 其他 Mod 和 GitHub 项目中的可验证先例。

外部资料适合发现术语和路径，本地数据决定实际键名、字段、作用域与数值。引用论坛、Wiki、仓库或特定版本时，若内容可能变化，应联网核实。

## 建立最终数据库

Victoria 3 Mod 的判断对象不是单个文件，而是所有启用内容按加载顺序形成的最终数据库。对相关目录执行：

1. 收集原版顶层定义；
2. 找出每个依赖对相同键的创建、完整替换、字段注入及目录级替换；
3. 按实际加载顺序合并；
4. 记录最终定义来源、列表顺序和引用关系；
5. 再决定目标 Mod 应注入、替换还是新增对象。

普通同名顶层键、`replace_path` 和依赖所用的扩展操作并不等价。对 `INJECT`、`REPLACE` 等写法，只在当前游戏或依赖中找到有效先例后使用。

## 搜索方法

- 用 `rg --files` 了解目录拓扑，再用 `rg -n` 搜索定义和引用。
- 同时搜索技术 ID、相关字段名、调用方和本地化键。
- 对引用链按“调度入口 → effect/trigger → 数据对象 → modifier/define”向下追踪。
- 对冲突按同一顶层键汇总，而不是按文件名猜测。
- 对列表型数据保留顺序；顺序可能代表 UI、优先级或升级关系。

## 选择覆盖方式

- 只需追加独立字段时，优先最小注入。
- 需要删除、重排或改写内部控制流时，通常需要完整替换或复制后改写。
- 完整替换应标明上游来源和版本敏感性，并验证没有遗漏后续加载 Mod 的变化。
- 适配两个系统时，明确每一方负责的入口、设置、状态、实际效果和回滚，避免双方同时写同一对象。
- 部分覆盖比完全不覆盖更危险时，应选择完整接管一个清晰边界，或保持原系统独占，而不是留下竞争写入。

## 兼容性清单

至少记录：

- 目标键最终由谁定义；
- 目标 Mod 是否必须最后加载；
- 是否需要声明依赖；
- 新游戏与旧存档行为是否不同；
- 上游更新后哪些覆盖报告或生成步骤需要重跑；
- 哪些对象有意不适配，以及原因。

把持久变量、事件目标、journal 状态、动态 modifier 名称和生成 ID 视作存档接口。含义改变时使用新键或迁移逻辑。
