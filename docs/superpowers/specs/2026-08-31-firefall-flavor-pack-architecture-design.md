# FFPA Firefall 风味合集架构设计

日期：2026-08-31
状态：书面规格已确认，首轮身份重定位已实施

## 1. 目标

把已经完成全局平衡、建筑清理和自动 PM 兼容剥离的当前项目，正式定位为面向固定加载环境的单一风味合集：

- 玩家可见名称：`FFPA — Firefall Flavor Pack`；
- Mod ID：继续使用 `com.wyb.2050-firefall-personal-adapter`；
- Victoria 3：继续支持 `1.13.*`；
- 固定运行环境：`2050: The Fire Falls` 与 `[1.13] Tech & Res`；
- 当前第一个内部风味模块：东地中海；
- 未来可继续加入其他国家或地区的风味预设。

采用“一个物理 Mod、多个内部地区模块”的架构。发布、启用和依赖管理以整个风味合集为单位；运行时代码、持久状态、本地化和覆盖登记按国家或地区明确归属。

本次重定位不改变现有东地中海功能、数值、技术 ID、事件 ID、变量含义、调度频率或存档状态。

## 2. 非目标

- 不再把东地中海身份、共同体状态机、地区建设和西方整合拆成多个物理 Mod。
- 不把已经迁出的 Core Balance、Building Pruning 或 Auto PM Adapter 功能重新并入。
- 不在本次重定位中新增第二个国家或地区风味模块。
- 不为了目录或命名整洁而重命名现有事件、变量、JE、modifier、trigger、effect 或本地化键。
- 不增加尚无玩家需求的地区开关、游戏规则或通用风味框架。
- 不改变当前目录名；目录迁移与 Workshop 发布身份变更需另行设计。
- 不因名称调整自动提升版本号。版本只在实际发布或用户明确要求时变更。

## 3. 采用方案

采用单一发布包、内部模块化方案：

```text
FFPA — Firefall Flavor Pack
├─ 发布外壳
│  ├─ metadata
│  ├─ README / AGENTS
│  └─ 共享本地化文件格式约定
├─ 东地中海模块（现有）
│  ├─ TUR / BYZ 身份与成立链
│  ├─ 日志、迁移与共同体状态机
│  ├─ 帝国地区建设
│  └─ 西方整合事件桥
└─ 未来地区模块
   ├─ 自有静态定义与覆盖
   ├─ 自有状态机与事件 namespace
   ├─ 自有 on_action 包装入口
   └─ 自有英文与简体中文本地化键
```

未采用的方案：

- **共享核心加地区子 Mod**：虽然可以按地区选择启用，但会重新引入依赖链、加载顺序和桥接包维护成本；当前没有独立启停需求。
- **完全扁平的单体实现**：发布简单，但随着地区增加会导致事件、持久变量、共享文件和覆盖对象失去所有者。

物理 Mod 的边界由“是否需要独立启用、是否有不同依赖、是否存在不可共存的覆盖”决定，而不是由脚本之间是否能划分职责决定。所有规划中的风味内容共享 Firefall 与 Tech & Res 依赖，因此当前没有继续拆包的必要。

## 4. 发布身份与依赖

### 4.1 保持稳定的身份

`.metadata/metadata.json` 实施时只调整玩家可见名称和对应简介：

- `name` 改为 `FFPA — Firefall Flavor Pack`；
- `id` 保持 `com.wyb.2050-firefall-personal-adapter`；
- `version` 暂时保持 `1.2.0`；
- `supported_game_version` 保持 `1.13.*`。

保留 Mod ID 能维持 Launcher 配置和既有发布身份的连续性。显示名称变化不需要运行时迁移。

### 4.2 固定依赖环境

合集继续硬依赖：

- `2050: The Fire Falls`：`alter_time_2050_fire_falls`；
- `[1.13] Tech & Res`：`tech.res`。

未来加入合集的地区风味默认必须适配同一最终数据库。如果某项内容需要新的硬依赖、面向原版独立运行，或必须覆盖另一个互斥大型 Mod，应在加入前重新判断发布边界，不能静默扩大整个合集的依赖集合。

已经迁出的四个外部包仍与风味合集保持独立：

- `2050-firefall-core-balance`；
- `ffpa-building-pruning`；
- `ffpa-building-pruning-techres`；
- `ffpa-techres-auto-pm-adapter`。

风味合集不得复制、重新定义或调用这些包的自有运行时接口。

## 5. 内部模块边界

### 5.1 东地中海模块

现有东地中海内容整体作为一个内部模块维护，不再物理拆分。它完整拥有：

- `BYZ` 身份、GRE → BYZ 成立链及相应覆盖；
- TUR/BYZ 政体、政府称谓、文化、旗帜、动态国名和党名；
- TUR/BYZ 日志、三轴共同体状态机、迁移与一次性事件；
- 15 项帝国地区建设 JE、完成变量和 `ffpa_region_*` 州 modifier；
- 地区建设通向西方整合事件的查询 trigger、检查 effect 和事件；
- 对应的英文与简体中文本地化。

身份、状态机、地区建设和西方整合仍可在代码评审中区分所有者，但它们属于同一发布模块，不需要跨 Mod 稳定接口。

### 5.2 未来地区模块

每个新地区模块必须能够回答：它提供什么内容、由什么入口启动、依赖哪些最终数据库对象、拥有哪些持久状态和覆盖键。

新增模块遵守以下隔离规则：

- 文件名使用清晰的地区或国家前缀；
- 新事件使用独立 namespace，不复用 `ffpa_flavor`；
- 新变量、JE、modifier、trigger、effect 和本地化键使用地区或国家前缀；
- 自有旧存档迁移由本模块的幂等 ensure effect 负责；
- 不直接读取另一地区的临时变量；确有联动时导出命名明确的 scripted trigger 或 scripted effect；
- 覆盖原版或上游顶层键时登记来源、加载顺序、覆盖原因和预期差异。

现有 `ffpa_flavor.*` 事件 namespace、`ffpa_tur_*`、`ffpa_byz_*`、`ffpa_region_*` 及版本化变量视为东地中海的既有存档 API，不因新的命名规范而重编号或重命名。

## 6. 共享接缝

单一物理 Mod 不等于所有地区共享内部状态。共享接缝只承担装配职责：

- **metadata**：描述整个合集的固定依赖与发布身份；
- **README / AGENTS**：登记模块清单、加载顺序、覆盖风险和维护规则；
- **原版 on_action 数据库**：各地区登记唯一的轻量包装入口；
- **本地化文件**：可以继续按语言集中存放，但键的所有权归各地区模块；
- **跨地区桥接**：只有出现真实联动需求时才建立稳定 trigger/effect，不预建通用框架。

每个地区优先使用自己的 on_action 文件和包装 ID。高频入口只做轻量条件判断，避免因地区数量增加而在月度 pulse 中重复遍历全世界国家、州或建筑。

## 7. 数据流与存档兼容

现有东地中海调用链保持不变：

1. 国家成立、游戏启动、月度国家脉冲和首次选举进入东地中海包装入口。
2. 幂等 ensure/migration effect 补齐旧存档日志、状态和版本化标记。
3. TUR/BYZ 日志及事件推进共同体、首都工程和有限风味事件。
4. 地区建设 JE 写入既有完成变量并向实际工程州发放对应 modifier。
5. 西方整合检查只通过已登记的完成状态查询触发一次性事件。

显示名称改变不触及以上流程。以下对象继续作为存档接口保留：

- 所有现有 `ffpa_flavor.*` 事件 ID；
- `ffpa_tur_*`、`ffpa_byz_*`、`ffpa_region_*` 变量和对象；
- 带 `_v1`、`_v2` 的迁移与一次性状态；
- 现有 JE、modifier、event target、动态 modifier 和覆盖键。

未来模块必须使用新的 ID 空间，不能借重构之名占用、重释或删除东地中海的既有持久 ID。

## 8. 实施范围

本设计通过书面复核后，首轮实施只进行身份重定位：

1. 把 metadata 的玩家可见名称改为 `FFPA — Firefall Flavor Pack`，同步更新简介但保持 ID、版本和依赖不变。
2. 更新 README 标题、项目定位和未来扩展说明。
3. 更新 AGENTS 的项目目标、模块边界、命名规则和推荐拆分顺序，明确东地中海不再是待拆对象。
4. 搜索并更新仍把当前包称为 Personal Adapter 的现行说明；历史拆分设计中的旧名称作为历史事实保留。
5. 不修改任何游戏运行时脚本或本地化键。

只有在加入第二个地区、现有共享文件已经影响所有权判断，或出现真实跨地区接口时，才进行进一步的内部文件整理。
